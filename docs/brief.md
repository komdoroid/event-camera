# ブリーフ（メインエージェントがヒアリング後に記入）

ステータス: 機能は承認済み（2026-10-21）／デザインは案2「ゆるい手描き・絵日記」をいったん採用（2026-10-21）

## 実現・検証したいこと（1文）
結婚式などのイベントで「撮影 → 現像 → 自動でできたオリジナルアルバムを、ホストだけでなくゲストも買う」という流れを通しで見せ、**イベント単位の課金ではなく、アルバム販売で収益を上げる方向性**が成り立つかをチームで比較・判断できるようにする。

## 背景・差別化
- 類似アプリ Pimorio（2026-10-14 v2.0.0、iPhone）は、アプリ不要のQR参加・グループ合計の枚数制限・翌朝7時の一斉現像を、無料・課金なしで実現済み。想定場面は友達同士の集まり
- チームメンバーの1人が、QR撮影〜写真一覧までの最低限のプロトタイプを作成済み
- そのため撮影と現像は最小限の土台にとどめ、**現像後のアルバムと購入体験**を作り込んで差をつける。場面は結婚式・イベントに絞る

## 誰が・どんな場面で使うか
- ホスト（新郎新婦・幹事）: イベントを作ってQRを掲示し、終わったら「現像」する。アルバムを確認・購入し、写真を一括ダウンロードする
- ゲスト（披露宴の参列者など）: QRからブラウザで撮影する。現像後に届いたアルバムを見て、気に入れば自分用に購入する

## 成功の体験（これが通しで動けば成功）
1. ホストがイベントを作成すると、QRコードが表示される
2. ゲストがスマホでQRを読み、アプリのインストールなしで3タップ以内に1枚目を撮れる。撮った写真は見えず、残り枚数だけが減る
3. ホストが「現像」ボタンを押すと、全員の写真がテンプレートに自動で並び、アルバムとして見られるようになる
4. ゲストもホストもアルバムを開くと、価格と購入ボタンが表示され、モックの決済を経て購入完了画面になる
5. ホストは写真一覧を見て、一括ダウンロードできる

## 画面の流れ（2026-10-21 確定）
- ゲスト: QRを読む → カメラ（全画面）→ 撮り切ると現像待ち → ホストが発刊したあと同じURLを開く → 発刊のお知らせ → アルバム → 購入 → 完了
- ホスト: イベント作成 → QR表示 → 管理（撮影数・発刊ボタン）→ 写真一覧・ダウンロード

## 追加の決定（2026-10-22）
- ホストの「マイイベント」一覧を追加する（ログインなし。この端末で作ったイベントの一覧から、各管理画面へ進む）。案 A
- 目的: **モバイルアプリにしたときの操作感と見た目を、チームで共有する**。ホスト側を、ホーム画面に追加して使えるアプリらしい作りにする
- アカウント（複数端末での同期・プロフィール）は引き続き作らない。本番化の課題として記録する

## 方針の変更（2026-10-25）
- **結婚式専用ではなく、さまざまなイベント向けのサービスとして設計する**（Kazuki の指示）。サービス名は「絵日記カメラ」、アルバムの基本の題名は「みんなの絵日記」。結婚式は種類の1つ
- 全体の UX 設計は `docs/design.md`。今日（10/25）は、その P0 を仕上げる
- 2026-10-25 追加: **見た目をもっとカラフルに**（絵日記の雰囲気は残す）。「クレヨン箱」の方向で、淡い青・ピンクに黄 #ffd96a・ミント #9fe0c4・オレンジ #ffb27a・むらさき #c7b3f0 を足す。イベントの種類ごとにテーマ色、アルバムのページごとに色を回す。範囲は全画面（カメラは黒のまま）
- 2026-10-25 追加: **書体を、やわらかく楽しい印象に変える**。見出し・ボタン・大きな数字は Kiwi Maru、本文は Zen Maru Gothic（案 A。Klee One・Yomogi はやめる）。カメラ画面の書体は今のまま
- 2026-10-25 追加: カメラの巻き上げを、**画面右下にのぞく実物のようなギザギザのダイヤル**にする。スワイプの量に合わせて回り、巻き上げきると「カチッ」と止まる

## 必須の機能
- スマホ向けWebアプリ（PWA）。ブラウザのカメラで撮影し、R2へ署名付きURLで直接アップロードする
- イベント作成とQR表示（ホスト）
- 枚数制限（イベントごとの設定値。詳細は下の「仮説」を参照）
- 現像前は写真を見られないこと。現像はホストがボタンで行う
- 現像時のアルバム自動生成（テンプレートに写真を自動で並べる）
- アルバムの閲覧と購入フロー（価格表示 → 購入 → 完了。決済はモック）
- ホスト向けの写真一覧と一括ダウンロード

## 今回はやらない機能
- ネイティブアプリ
- 実際の決済（Stripe など）と、印刷・配送の実手配
- アルバムの手動編集（写真の選択・入れ替え・並べ替え）
- 決まった時刻での自動現像（本番では「翌朝に自動」などを想定するが、デモではホストのボタンで代用）
- ゲストの名前入力・アカウント・ログイン（ゲストは端末ごとに自動で識別する）
- メール配布（Resend）
- 写真を1年間保存する仕組みなど、本番向けの運用

## こだわり（見た目・技術）
- フロント: Vite + React（PWA）を Cloudflare Pages で配信する
- バックエンド: Cloudflare Workers + D1 + R2（docs/project.md のとおり）
- スマホでの操作感を最優先する。比較の場で「このまま出せそう」と感じてもらえる完成度を目指す

### デザインの方針（2026-10-21 夕方に更新）
- **カートゥーン調で、白を基調にする**。雑誌案（現代風・古い雑誌の年代4案）とカジュアル案はすべて却下
- 候補は2つ。比較用のイメージ（タスク T0e）を見てから決める
  - **太線フラット**: 黒い太い輪郭線と平塗りの色
  - **ゆるい手描き**: 細いペンの落書き風、余白が多め
- アルバムのコンセプト（雑誌・コミック・絵日記など）は、スタイルごとにメインエージェント側から提案する
- **2026-10-21: 案2「ゆるい手描き」で、アルバムは「ふたりの絵日記」をいったん採用**。参考は `web/mock/cartoon-study.html` の案2（Klee One と Yomogi、揺れた細い線、淡い水色とピンク、余白は多め）。「現像」は「絵日記がとどきました」として見せる
- カメラ画面は **A（黒の全画面ファインダー）のまま**。カートゥーン調にするのは、現像待ち以降の画面とホスト画面
- カメラの仕様: 独立した全画面、使い捨てカメラのような残り枚数のカウンター、3分割のグリッド線、画面端の日付・時刻を表示する。シャッターを押すと画面が一瞬暗くなり、**次を撮るにはスワイプで巻き上げる**。写真は見せない。1枚目は巻き上げ済みの状態から始め、「3タップ以内に1枚目」を守る
- **見た目の決定と実装は並行して進める**。API・撮影・購入の仕組みなど、見た目に左右されない部分から実装を始める
- 場面: デモは結婚式で作る。文言やテンプレートは、ほかのイベントにも差し替えられる設計にする
- これまでのモック: `web/mock/album-mock.html`（画面の流れとカメラ A の参考）、`web/mock/era-study.html`（却下）

## 仮説のまま進めている点（確認したい）
- **ホストのアプリの形**（2026-10-22、メインエージェントの判断）: 下部のタブは「ホーム（マイイベント）」と「つくる」の2つ。ホーム画面に追加したときの起動先は `/host`。トップページ `/` は `/host` に移す。ゲストの画面は今のまま（タブなし）
- **枚数制限**: Pimorio は「グループ全員の合計」。ここではゲスト1人ごとの上限（仮に27枚）をイベントの設定値として持ち、数値や仕組みは後から変えられるようにする
- **アルバムの中身**: ゲストとホストが買うアルバムは同じ内容（イベントの全写真を自動レイアウトしたもの）にする。ゲストごとの個別化はしない
- **商品と価格**: 「デジタルアルバム（例: ¥500）」と「印刷フォトブック（例: ¥3,000）」の2種類を表示する。価格は見せ方のための仮の値
- **アルバムのテンプレート**: 選ばれたスタイルで1種類（表紙・中のページ数パターン・最後のページ）用意する
- **写真のアップロード**: R2 の S3 互換キーを発行しなくて済むように、Worker が発行する期限付きの署名URLに、クライアントから直接 PUT する。Worker はそれを R2 バインディングで保存する（docs/project.md の「署名付きURLで直接アップロード」をこの形で満たす）
- **デプロイ**: 2026-10-21 に Kazuki がデプロイを許可した。手順はメインエージェントが案内し、ログインと実行は Kazuki が行う
- **公開URL**: スマホで開けるURLにするには `wrangler deploy` と Pages への公開が必要になる。実行は Kazuki さんが行う（10/24 中を想定）
- **会場で使うデモ用の端末**: iPhone Safari と Android Chrome の両方で動けばよいものとする
